# Revisão da spec F6 — o plano de testes prova o que promete?

**Spec:** docs/specs/F6-portabilidade-hardening.md @ da25cd6
**Veredito:** REQUEST CHANGES
**Achados:** 3 Critical, 4 Important, 2 Minor

## Resposta obrigatória — Eixo 1: E2E-F6-02 é falso-verde por coincidência de id?

**Veredito: risco DESCARTADO com evidência.** A cadeia de garantias que torna a coincidência
impossível sob operação normal:

1. `Tag.id`/`Project.id`/`OpcConnection.id` são `BigInteger, Identity(always=True)` (`packages/ottima-core/src/ottima_core/models/tag.py:22`, `.../models/project.py:12`, `.../models/connection.py:22`). `always=True` proíbe até `INSERT` explícito de id (exigiria `OVERRIDING SYSTEM VALUE`, que nenhum código do projeto usa) — nenhuma linha nova pode nascer com um id escolhido por quem chama, só pelo `nextval()` da sequence.
2. A cadeia de exclusão é `ON DELETE CASCADE` no banco, não só no ORM: `Tag.connection_id → opc_connections.id ondelete="CASCADE"` (`models/tag.py:24-26`) e `OpcConnection.project_id → projects.id ondelete="CASCADE"` (`models/connection.py:24-26`). `DELETE /api/projects/{id}` faz `await db.delete(project); await db.commit()` (`services/api/src/ottima_api/routers/projects.py:69-74`) — exclusão real, não soft-delete, e só é permitida com `is_active=False` (409 se ativo).
3. Sequences Postgres **não são transacionais e nunca voltam por `DELETE`**: uma vez consumido, um id fica "queimado" para sempre — só `ALTER SEQUENCE ... RESTART` ou `TRUNCATE ... RESTART IDENTITY` reabririam a faixa. Busquei essas duas expressões no repo inteiro (`grep -rn "RESTART IDENTITY\|TRUNCATE"`): a única ocorrência em código de teste é `services/flow-runtime/tests/conftest.py:69` (`TRUNCATE flows, tags, opc_connections, projects CASCADE`) — **sem `RESTART IDENTITY`** — e é usada pela suíte de integração do flow-runtime (banco `testcontainers`, sessão própria), nunca pela suíte `tests/e2e/`. A suíte e2e não tem acesso a SQL direto: só fala com o banco via API HTTP.
4. O banco do stack e2e é **persistente por padrão**: `deploy/docker-compose.yml:150-151` declara `pgdata` como volume nomeado (não `tmpfs`, não anônimo por container efêmero), e `tests/e2e/conftest.py:17-19` documenta o motivo do `RUN_ID`: "o banco do stack é persistente e nada pode colidir com a rodada anterior". `down -v` só ocorre "com autorização explícita + dump prévio" (spec §9.3, §1.2). Mesmo no caso hipotético de um `down -v` autorizado (banco genuinamente vazio), o argumento não muda: dentro de uma ÚNICA execução do teste (criar → exportar → `DELETE` → importar), a sequence começa em 1 e sobe monotonicamente — não há nenhum ponto entre o `DELETE` e o `import` em que algo a reinicie. `tests/README.md:6-7` confirma que essa é a convenção assumida de toda a suíte: "o banco do stack é persistente: os testes usam sufixo único por execução... rodar a suíte duas vezes seguidas dá verde nas duas."
5. Ainda que, por alguma falha de tradução, uma referência antiga sobrevivesse (ex.: tradutor deixa `tag_id` velho verbatim), a validação de camada 4 não faz busca global: `_check_tags`/`_check_pid_tag` (`packages/ottima-core/src/ottima_core/flowgraph/validate.py:169,580-589`) resolvem `tags.get(tag_id)` contra o **mapa de tags do projeto/flow sendo validado** (materializado após o `flush()` das tags novas, por §3.2-4 item 4) — não contra a tabela `tags` inteira. Um id órfão só passaria se coincidisse com um id que já pertence ao PRÓPRIO projeto novo, o que a Identity torna impossível (item 1-3).

**Conclusão:** a garantia de A-9 ("a sequence já avançou, os ids são necessariamente diferentes")
está correta e é mais forte do que o texto da spec deixa explícito — mas a spec não cita nenhuma
dessas cinco camadas de evidência (Identity `always`, CASCADE de banco, sequence não-transacional,
volume persistente, escopo por-projeto da validação). Isso não é bug de código, é lacuna de
justificativa: um revisor sem acesso ao código (ou um engenheiro futuro decidindo se pode rodar
a suíte contra um Postgres gerenciado com replicação lógica ou com `pg_repack`, cenários onde
alguém *poderia* querer resetar sequences) não tem como saber, só pela spec, que o risco é
mecanicamente impossível. Ver TST-01 para o achado residual real deste eixo — que não é o
descrito na tarefa.

## Achados

### TST-01 — E2E-F6-02 nunca testa desambiguação por conexão, o caso que motivou `tag_ref` ser objeto [Important]
**Seção:** §2.2-2 · §9.2 (E2E-F6-02) · Anexo A-2
**Problema:** A-2 justifica `tag_ref` ser `{connection, tag}` (objeto) e não a string `"conexao/tag"` exatamente porque nomes de tag só são únicos **por conexão**, não por projeto (`Tag.name` — `models/tag.py:33`, `uq_tags_connection_name` em `connection_id+name`). Ou seja, o cenário de risco real que a forma-objeto foi desenhada para resolver é: duas conexões do MESMO projeto com uma tag de MESMO nome (ex.: duas conexões a dois gateways diferentes, ambas com uma tag `"TT-101"`). Um tradutor com bug que indexasse o mapa de tags só por nome (ignorando `connection`) resolveria a referência errada — nesse produto, "escrever na tag errada" é o pior modo de falha possível (contexto do produto: efeito físico em planta). `E2E-F6-02`, como descrito em §9.2, usa "conexão segura + tags + flow MPC↔TFS" — a fixture padrão herdada de `AmbienteMpc`/`grafo_mpc_tfs` (`tests/e2e/conftest.py:445-479,612-653`) tem **uma única conexão**. Nenhum cenário do §9.1 (unit) ou §9.2 (E2E) descrito na spec menciona explicitamente duas conexões com tags homônimas no mesmo bundle.
**Evidência:** `docs/specs/F6-portabilidade-hardening.md` §2.2-2 (decisão de forma objeto) · Anexo A-2 · `tests/e2e/conftest.py:445` (`AmbienteMpc` — 1 `conn_id`) · `models/tag.py:33` (unicidade por conexão, não por projeto).
**Consequência:** Um bug de tradução que resolve `tag_ref` só por nome (ignorando o campo `connection`) passaria por TODA a suíte descrita na spec — E2E-F6-02 nunca cria a condição de homonímia entre conexões que exporia esse bug, e o cenário só teria uma conexão para escolher errado.
**Correção sugerida:** Em E2E-F6-02 (ou num teste unitário de tradução dedicado em §9.1), o projeto de origem precisa ter **duas conexões**, cada uma com uma tag de mesmo nome (ex.: `TT-101` em `gateway-1` e em `gateway-2`), com pelo menos uma delas referenciada por um bloco `opc_read`/`opc_write` ou por um `pid` de MPC. Depois do round-trip, o teste deve confirmar que o `tag_id` resolvido no destino aponta para a tag da conexão CORRETA (ex.: lendo o `node_id`/valor físico de volta, não só que "o grafo validou").

### TST-02 — Overrun: "`grafo_mpc_tfs` com o mesmo config pesado" é irrealizável como está escrito [Critical]
**Seção:** §7.2 (tabela RNF-09, linha Overrun) · §7-4
**Problema:** A linha da tabela diz: "**reescrito**: `_grafo_overrun` (dummy `NODE_SINE`) → `grafo_mpc_tfs` com o mesmo config pesado". Isso descreve uma substituição direta que a base de código atual não permite, por duas razões independentes e cada uma suficiente:
1. `grafo_mpc_tfs(ambiente, *, valor_dv, mpc_id)` (`tests/e2e/conftest.py:612-653`) **não recebe config** — ele chama internamente `_config_mpc_malha(ambiente)` (`conftest.py:531-561`), que é hardcoded: 2 MVs (`mv_pid` com `pid`, `mv_direta` sem `pid`), 1 CV (`cv_1`), 1 restrição (`co_1`), 1 DV. Não há parâmetro para injetar `_config_mpc_pesado()` (4 MVs, 6 CVs, 0 restrições — `tests/e2e/test_f4_failure.py:44-45,74-97`).
2. Mesmo se `grafo_mpc_tfs` ganhasse esse parâmetro, o bloco `tfs` é travado em exatamente 2 entradas × 2 saídas por **regra de parse, não convenção**: `_parse_tfs_config` rejeita qualquer `matrix` que não tenha `len(matrix) != 2` ou alguma linha com `len(row) != 2` (`packages/ottima-core/src/ottima_core/flowgraph/parse.py:326-327`; comentário confirmando em `parse.py:87`: "sempre 2x2"). Uma TFS não pode alimentar 6 CVs. O próprio módulo `test_f4_failure.py` já documenta, no docstring de topo, por que o overrun **não** usa `grafo_mpc_tfs` hoje: "o overrun (06) usa um config PRÓPRIO, propositalmente pesado... com MVs diretas (sem `pid`): não precisa de malha física pra provar que o orçamento estoura" (`test_f4_failure.py:3-6`).

A dimensão de 340 (`_N_MV_PESADO=4 × _N_ROWS_PESADO=6 × 14`, comentário em `test_f4_failure.py:44-45`) e a topologia de `grafo_mpc_tfs` (2 MVs, 1 CV, 1 restrição — dimensão ≈10 com `theta=0`) são shapes incompatíveis. Para conciliar "malha fechada por TFS" com "mesmo config pesado" um implementador precisaria: (a) encolher o config pesado para caber em 2 MVs/2 saídas — invalidando os números exatos que a spec cita (dimensão=340, Np=120) — ou (b) empilhar múltiplos blocos `tfs` (um por par de CVs) num grafo novo, não especificado, ou (c) mudar a assinatura de `grafo_mpc_tfs` para aceitar config externo E ainda assim só alimentar 2 dos 6 CVs pela TFS (os outros 4 continuariam dummy) — o que contradiz "fecha a malha por `grafo_mpc_tfs`" da tabela §7.2, que lista o overrun como um dos "quatro itens... todos fechando a malha por `grafo_mpc_tfs`".
**Evidência:** `tests/e2e/conftest.py:531-561,612-653` · `tests/e2e/test_f4_failure.py:1-7,36-49,74-136` · `packages/ottima-core/src/ottima_core/flowgraph/parse.py:86-87,322-327`.
**Consequência:** Tarefa inexecutável como escrita. Se implementada ao pé da letra ("chamar `grafo_mpc_tfs` com o config pesado"), o código simplesmente não compila/roda (função não aceita o parâmetro). Se um implementador resolver a contradição por conta própria, o resultado varia por decisão pessoal — dimensão real, determinismo do overrun e tempo de execução do cenário ficam todos em aberto, exatamente o tipo de ambiguidade que dois implementadores resolveriam diferente. A pergunta "quanto tempo o cenário passa a levar" (tarefa, eixo 2) fica sem resposta possível até essa contradição estrutural ser resolvida — não é uma questão de recalibrar timeout, é uma questão de a topologia não caber.
**Correção sugerida:** A spec precisa escolher e escrever explicitamente uma de três formas, porque a atual não é implementável: (1) reduzir a config pesada a 2 MVs / 2 saídas TFS e inflar `theta`/`tss` para ainda cruzar dimensão>150 e Np=120 sob esse teto (recalcular e publicar os números novos — não são mais 4 MVs/6 CVs); (2) manter a topologia pesada de 6 CVs e criar uma variante de `grafo_mpc_tfs` (não a mesma função) com múltiplas TFS de 2 saídas cada, cobrindo pares de CVs, aceitando um grafo maior; (3) admitir explicitamente que overrun mistura TFS real (para alguns CVs) com dummy (para o resto) e documentar que isso só fecha a malha PARCIALMENTE, revisando a frase "todos fechando a malha por `grafo_mpc_tfs`" no §7.2. Qualquer que seja a escolha, a spec deve fixar os números novos (dimensão, Np, MVs, CVs) e o tempo de solve esperado — o "~13-17s" atual não se aplica sem recálculo.

### TST-03 — Hot-swap: reescrita para `grafo_mpc_tfs` elimina o `mpc2` (irmão de controle), a peça central da prova [Critical]
**Seção:** §7.2 (tabela RNF-09, linha Hot-swap)
**Problema:** A tabela diz: "**reescrito**: `_grafo_hot_swap` (dummy) → `grafo_mpc_tfs`". O teste atual `test_e2e_f4_10_ws_fanout_e_hot_swap` (`tests/e2e/test_f4_ws.py:210-319`) usa `_grafo_hot_swap` (`test_f4_ws.py:156-183`), que constrói **dois** blocos `mpc` independentes (`mpc1`, `mpc2`) — o próprio módulo documenta: "Dois blocos `mpc` independentes e diretos: `mpc1` recebe o hot-swap (peso variável), `mpc2` é o irmão que nunca muda — prova de preservação de estado" (`test_f4_ws.py:4-6,157-158`). A prova do cenário depende estruturalmente do segundo bloco: depois do `PUT` que altera só `mpc1`, o teste assina `/ws` dos dois blocos e afirma `pos_swap_2["modes"] == {"local_remote": "remote", "man_auto": "auto"}` — **`mpc2` nunca sheda** (`test_f4_ws.py:301-310`) — provando que o hot-swap troca só quem mudou.

`grafo_mpc_tfs` (`tests/e2e/conftest.py:612-653`) produz **um único** nó `mpc` (parametrizado por `mpc_id`, default `"mpc1"`); não existe segundo bloco, e `AmbienteMpc` (`conftest.py:445-451`) só tem 4 tags — as do `pid` de UM `mv_pid` (`write`, `mode_cmd`, `readback`, `mode_read`). Substituir `_grafo_hot_swap` por `grafo_mpc_tfs` ao pé da letra apaga `mpc2` do grafo: não há mais como fazer a asserção-chave do cenário ("o irmão não mexeu"). Chamar `grafo_mpc_tfs` duas vezes com `mpc_id="mpc1"` e `mpc_id="mpc2"` não resolve — as duas chamadas compartilhariam o MESMO `ambiente.write`/`ambiente.readback` (a única MV física do `AmbienteMpc`), ou seja, dois blocos MPC diferentes escrevendo na MESMA tag física — exatamente o tipo de conflito de escrita simultânea na malha que o produto trata como intolerável, e nada no runtime impede isso na validação de grafo (não há checagem de MV.pid.write_tag_id repetido entre blocos `mpc` diferentes).
**Evidência:** `tests/e2e/test_f4_ws.py:4-6,156-188,258-262,283-286,301-319` · `tests/e2e/conftest.py:445-479,612-653`.
**Consequência:** Assim como o overrun (TST-02), a reescrita como descrita é inexecutável — ou perde a prova de preservação de estado do irmão (o núcleo do cenário, citado na própria RNF-09 como "hot-swap"), ou exige uma segunda malha física completa (mais 4 tags, possivelmente mais uma conexão) que a spec não menciona nem provisiona.
**Correção sugerida:** Documentar explicitamente que o hot-swap RNF-09 precisa de uma segunda malha real (novo conjunto de 4 tags de `pid` para um `mpc2` com sua própria MV física, ou reaproveitar `mv_direta` — que hoje não tem `pid` — promovendo-a a uma segunda malha com sua própria TFS), OU aceitar e registrar formalmente que `mpc2` (irmão de controle) permanece dummy/direto mesmo na reescrita (só `mpc1` fecha por TFS) e ajustar a frase da tabela §7.2 de "todos fechando a malha por `grafo_mpc_tfs`" para refletir essa exceção pontual do hot-swap.

### TST-04 — Import/export com nome duplicado *dentro do próprio bundle* nunca é testado por nome [Important]
**Seção:** §3.2-4 (camada 3) · §9.1 · §9.2 (E2E-F6-03)
**Problema:** §3.2-4 item 3 lista, entre as reprovações da camada 3 (Referências internas): "nome duplicado dentro do próprio bundle" — mas essa regra nunca aparece de novo em nenhum cenário nomeado. O §9.1 (unit) só diz genericamente "`/projects/import` (as 4 camadas...)" sem listar esse caso. `E2E-F6-03` (§9.2) enumera seis recusas explícitas — `schema_version`, `tag_ref` órfã, `exec_order` não contíguo, "nome duplicado" (mas este é o nome do **projeto** colidindo com um projeto JÁ EXISTENTE no banco de destino, 409, não o caso de duas entidades homônimas dentro do MESMO bundle, 422) — corpo grande, RBAC. Duas entidades homônimas dentro de um único bundle nunca aparecem: dois `flows` chamados "Coluna C-101" no mesmo bundle, ou duas `connections` chamadas "gateway-1", ou duas `tags` "TT-101" na mesma conexão dentro do bundle.
**Evidência:** `docs/specs/F6-portabilidade-hardening.md` §3.2-4 item 3 · §9.1 (bullet API) · §9.2 (tabela E2E-F6-03) · `models/flow.py:38` (`uq_flows_project_name`, únicidade real no banco que a camada 3 pretende antecipar).
**Consequência:** Sem um teste nomeado para esse caso específico, é fácil que a implementação da camada 3 confie só na `IntegrityError` do banco na hora do `INSERT` (que dispararia DEPOIS de já ter inserido outras entidades na mesma transação, obrigando rollback tardio em vez da checagem antecipada que a camada 3 promete) — ou pior, que dois `Flow`/`Connection`/`Tag` homônimos dentro do bundle simplesmente nunca sejam checados antes do `flush()`, e o erro que o usuário vê seja um `IntegrityError` traduzido genericamente (não a mensagem agregada pt-BR do §3.2-5), quebrando o contrato de erro único da API.
**Correção sugerida:** Acrescentar a E2E-F6-03 (ou a um teste unitário de camada 3): bundle com dois `flows` de mesmo nome ⇒ 422 com `detail` citando ambos; bundle com duas `connections` de mesmo nome ⇒ 422; bundle com duas `tags` de mesmo nome na mesma `connection` ⇒ 422 — todos ANTES de qualquer `INSERT`, confirmando "banco inalterado" nesses casos também (o §9.2 já promete isso para os outros cinco casos de E2E-F6-03; falta este).

### TST-05 — Falta teste de import com `pid` de MPC parcialmente preenchido no bundle [Important]
**Seção:** §2.2-3 · §3.2-4 (camada 4) · §9.1
**Problema:** `PidBinding` (`packages/ottima-core/src/ottima_core/flowgraph/mpc_config.py:58-70`) exige `write_tag_id`, `mode_cmd_tag_id` e `readback_tag_id` (só `mode_read_tag_id` é opcional). No bundle, o equivalente seria um `pid` com `write_tag_ref` presente mas `readback_tag_ref` **ausente da chave** (não "não resolve" — simplesmente não existe no JSON). §2.2-4/5 só descreve o caso "referência que não resolve" (chave presente, mapa não bate) como erro de camada 3; não existe menção ao caso "chave de referência ausente". A validação semântica (camada 4) É defensiva no nível de `MpcConfig` — `_parse_mpc_configs` (`packages/ottima-core/src/ottima_core/flowgraph/validate.py:406-424`) captura `ValidationError` do Pydantic e converte em uma linha agregada ("config não confere com a spec F4 §2.1"), então o `graph_json` JÁ TRADUZIDO (com `readback_tag_id` faltando) não quebra o import com 500 — isso É uma verificação positiva. Mas a etapa que falta especificar/testar é a **tradução em si**: se o código de tradução (`tag_ref` → `tag_id`, ainda não escrito) usar acesso não-defensivo a uma chave ausente (ex.: `config.pop("readback_tag_ref")` em vez de `config.get("readback_tag_ref")`), um `KeyError` não-tratado escapa ANTES de chegar à camada 4, e o import vira 500 em vez de 422 pt-BR agregado — quebrando o contrato universal de erro da API (`app.py:60-67`, citado no próprio §3.2-5).
**Evidência:** `mpc_config.py:58-70` · `validate.py:406-424` (camada 4 é robusta) · spec §2.2-3/4/5 (nunca menciona "campo ausente", só "referência que não resolve").
**Consequência:** Se ninguém testar esse caso especificamente, o primeiro cliente que exportar um bundle antigo (ou editado a mão) com um `pid` incompleto recebe um 500 sem diagnóstico em vez do `detail` pt-BR agregado prometido pelo aceite da fase.
**Correção sugerida:** Unit test em §9.1 (ottima-core): bundle com um `mpc` cujo `pid` tem `write_tag_ref`/`mode_cmd_tag_ref` mas SEM a chave `readback_tag_ref` ⇒ 422 com `detail` citando o campo faltando, nunca 500. Exigir na implementação que a função de tradução use `.get(campo, None)` para cada um dos seis campos (nunca `.pop()`/indexação `[]`), delegando a ausência para a validação de forma/semântica já existente reportar como "campo faltando".

### TST-06 — Mecanismo de teste de completude dos seis campos: implementável, spec não diz como [Important]
**Seção:** §2.2-3 · §9.1
**Problema:** A spec afirma: "a lista de tradução conferida contra `_CONFIG_KEYS` (`parse.py:19-25`) e contra os campos de `PidBinding` (`mpc_config.py:58-68`), para que um bloco novo com referência de tag esquecido vire vermelho" — mas não diz COMO a comparação é feita nem onde mora a "lista de tradução" que serve de lado esquerdo da comparação. Os anchors estão corretos (confirmado: `_CONFIG_KEYS["opc_read"]=("tag_id",)`, `_CONFIG_KEYS["opc_write"]=("tag_id",)` em `parse.py:20-21`; `PidBinding` em `mpc_config.py:58-70` com 4 campos terminados em `_tag_id`), mas a spec não propõe o mecanismo de introspecção nem exige que a lista de tradução (usada pelo tradutor de verdade em runtime) seja uma constante única, importável e comparável por teste — sem isso, "a lista vive num lugar só" (§2.2-3) é uma intenção, não uma garantia mecânica.
**Evidência:** `packages/ottima-core/src/ottima_core/flowgraph/parse.py:20-21` · `.../flowgraph/mpc_config.py:58-70`.
**Consequência:** Sem o mecanismo especificado, dois implementadores plausivelmente fariam: (a) uma lista hardcoded de nomes que o teste também hardcoda (o teste vira uma cópia da lista, não uma proteção — exatamente o "bug de campo" que a spec quer evitar) vs. (b) introspecção real contra os modelos Pydantic. Só (b) cumpre o objetivo declarado ("o esquecimento vira vermelho").
**Correção sugerida:** Mecanismo concreto proposto: expor uma única constante importável, ex. `TAG_REF_FIELDS: tuple[tuple[str, str], ...]` em `ottima_core` (par `"caminho.no.bundle"` → `"campo_no_banco"`), usada tanto pelo tradutor real quanto pelo teste. O teste de completude deriva o conjunto ESPERADO por introspecção — `{c for c in _CONFIG_KEYS["opc_read"] + _CONFIG_KEYS["opc_write"] if c == "tag_id" or c.endswith("_tag_id")}` ∪ `{nome for nome in PidBinding.model_fields if nome.endswith("_tag_id")}` — e afirma que esse conjunto é exatamente o conjunto de campos-destino em `TAG_REF_FIELDS`. Um campo novo terminado em `_tag_id` em qualquer um dos dois modelos aparece no lado "esperado" automaticamente; se não estiver em `TAG_REF_FIELDS`, o teste falha. Isso é implementável hoje, sem depender de nenhum código do F6 ainda não escrito — só depende da convenção de nome `_tag_id`/`tag_id` já em vigor nos dois modelos-fonte (verificada: é a convenção real, sem exceção, nos dois arquivos).

### TST-07 — Marcador `rnf09`: mecanismo funciona, mas a spec não registra o comando nem a mecânica do `-m` [Minor]
**Seção:** §7.1
**Problema:** A spec afirma "a suíte roda por seleção explícita" mas não escreve o comando, e a mecânica merece registro porque não é óbvia: `addopts = "-m 'not e2e and not slow'"` (`pyproject.toml:29`) é um argumento de linha de comando pré-pendurado, e o `pytest` usa `action="store"` para `-m` (não cumulativo) — logo, `-m rnf09` na linha de comando **sobrescreve** o `-m` do `addopts`, não faz "E" com ele. **Verifiquei empiricamente** (sandbox local, pytest reproduzindo a mesma config de `addopts`/`markers` do projeto): com `addopts = "-m 'not e2e'"`, `pytest -m rnf09` coleta corretamente só os testes marcados `rnf09` (que também são `e2e`), e descarta os `e2e`-apenas — sem precisar de `-o addopts=""` nem de `-m "rnf09"` combinado com negação explícita de `not e2e`. Isso é consistente com o padrão já em uso desde a F1: `CLAUDE.md:106` já documenta `pytest -m e2e tests/e2e -v` como o comando real da L2, e esse comando JÁ depende do mesmo mecanismo de sobrescrita (`-m e2e` sobrepondo `not e2e and not slow` do `addopts`) — é precedente direto, só nunca foi escrito explicitamente como regra.
**Evidência:** `pyproject.toml:27-30` · `CLAUDE.md:106` · reprodução empírica local (pytest 8.x, `tool.pytest.ini_options` idêntico ao do projeto).
**Consequência:** Mínima — o mecanismo funciona. Mas por não estar escrito, um implementador poderia "corrigir" um suposto problema que não existe (ex.: inventar `-o addopts=""` ou duplicar a expressão negando `e2e`), gerando um comando mais complicado do que o necessário e potencialmente divergente do padrão já documentado para as fases anteriores.
**Correção sugerida:** Registrar em §7.1 (ou no §9.3/CLAUDE.md, como as fases anteriores fizeram) o comando exato: `uv run pytest -m rnf09 tests/e2e -v`, com uma nota de que `-m` na linha de comando substitui — não intersecta — o `-m` do `addopts`.

### TST-08 — Regressão garantida: mudança de payload de `mpc_overrun` (§5.1) quebra `test_f4_failure.py:226` [Critical]
**Seção:** §5.1 · §9.2 (Regressão) · §7.2 (E2E-F4-06)
**Problema:** `blocks/mpc.py:456-463` hoje chama `self._emit_event(..., kind=KIND_MPC_OVERRUN, payload={})`. `publish_event` (`packages/ottima-core/src/ottima_core/bus.py:174-201`) sempre injeta `kind` no payload publicado: `final_payload = {"kind": kind, **payload}` (`bus.py:199`) — hoje isso produz `{"kind": "mpc_overrun"}`. O teste atual afirma essa forma **por igualdade exata**: `assert evento["payload"] == {"kind": KIND_MPC_OVERRUN}` (`tests/e2e/test_f4_failure.py:226`). Depois de §5.1 (`payload={"overruns": contador}`), o payload publicado passa a ser `{"kind": "mpc_overrun", "overruns": N}` — a igualdade exata do teste **falha sempre**, porque o dict ganhou uma chave. Isso não é hipotético: é uma consequência mecânica e certa da mudança, confirmada rastreando `_report_overrun` → `_emit_event` → `publish_event` linha por linha.

O agravante: `test_f4_failure.py:226` está dentro do MESMO teste (`test_e2e_f4_06_overrun_mantem_mv_e_alarme`) que o §7.2 já manda reescrever por outro motivo (TST-02). A spec trata a mudança de payload (§5.1) e a reescrita do grafo (§7) como itens INDEPENDENTES da tabela §1.1, sem nenhuma referência cruzada entre eles — um implementador que faça §5.1 como uma tarefa isolada (ex.: no plano F6a, runtime) e §7 como outra (plano F6c, suíte de testes), em ordens ou PRs diferentes, tem um caminho realista para deixar essa linha desatualizada mesmo reescrevendo o resto do teste em volta dela.
**Evidência:** `services/flow-runtime/src/ottima_flow_runtime/blocks/mpc.py:456-463` · `packages/ottima-core/src/ottima_core/bus.py:186,199` · `tests/e2e/test_f4_failure.py:226` · comparação de simetria com `flow_overrun` (`services/flow-runtime/src/ottima_flow_runtime/scheduler.py:253-261`, que já publica `overruns` par de outros campos, confirmando a forma nova esperada).
**Consequência:** Sem correção coordenada, a "suíte MPC↔TFS verde" e a "regressão de 41 cenários" (ambos requisitos do aceite, §9.2) ficam vermelhas nesse ponto específico assim que §5.1 for mergeado, mesmo que TST-02 seja resolvido corretamente.
**Correção sugerida:** Adicionar em §5.1 (ou como nota cruzada explícita entre §5.1 e §7.2) a instrução: "a asserção de payload em `test_f4_failure.py` (ou seu sucessor pós-reescrita do §7) passa a ser `evento["payload"] == {"kind": KIND_MPC_OVERRUN, "overruns": N}` com `N` coerente com `block.health()["overruns"]`". Isso também fecha a lacuna simétrica do §9.1 ("payload de `mpc_overrun` com `overruns`") apontando para o lugar exato onde a asserção unitária equivalente deveria nascer (`services/flow-runtime/tests/test_mpc_block.py`, no teste `test_overrun_mantem_mv_soma_contador_e_dedupe_do_evento`, linhas 399-424, que hoje só verifica contagem via `len(events.of_kind(...))`, nunca o payload).

### TST-09 — Idempotência de E2E-F6-02/03 depende de convenção não citada pela spec [Minor]
**Seção:** §9.2 (E2E-F6-02, E2E-F6-03) · §9.3
**Problema:** A pergunta se E2E-F6-02 (round-trip destrutivo) e E2E-F6-03 (nome duplicado) são re-executáveis sem limpeza manual tem resposta **sim**, mas por uma convenção que já existe no projeto e que a spec F6 não cita: `RUN_ID = f"{time.time_ns():x}"` (`tests/e2e/conftest.py:19`) sufixa nomes por execução, fixtures usam esse sufixo (`ambiente_mpc`: `sufixo = f"{request.module.__name__...}-{RUN_ID}"`, `conftest.py:459`), e o teardown sempre exclui o que criou (`admin.delete(f"/api/projects/{projeto['id']}")`, padrão repetido em `projeto_com_conexao`/`ambiente_mpc`). `tests/README.md:6-7` formaliza isso como invariante da suíte inteira: "rodar a suíte duas vezes seguidas dá verde nas duas". Nada em §7/§9.2 instrui explicitamente que E2E-F6-02 (que precisa recriar um projeto com o MESMO nome lógico do bundle após o `DELETE` do original) e E2E-F6-03 (que precisa colidir de propósito com um nome já existente) sigam essa convenção — ficam implícitos.
**Evidência:** `tests/e2e/conftest.py:17-19,369-386,459-479` · `tests/README.md:6-7`.
**Consequência:** Risco baixo — a convenção é forte, documentada e seguida em toda a suíte hoje. Mas E2E-F6-02 é o PRIMEIRO cenário a fazer `export → DELETE → import` do mesmo nome de projeto dentro de um teste; se implementado sem sufixo (copiando literalmente o exemplo do PRD §7.2, "Planta C-101"), a segunda execução da suíte falharia na criação do projeto de origem com 409 (nome já existente da rodada anterior, já que o de origem é diferente do reimportado).
**Correção sugerida:** Adicionar uma frase em §9.2 (E2E-F6-02/03): "nomes de projeto/conexão/tag seguem o padrão de sufixo `RUN_ID` de `conftest.py`, como os demais cenários E2E; a suíte precisa permanecer re-executável sem `down -v` (`tests/README.md`)".
