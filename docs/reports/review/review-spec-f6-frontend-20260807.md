# Revisão da spec F6 — implementabilidade no frontend React

**Spec:** docs/specs/F6-portabilidade-hardening.md @ da25cd6
**Veredito:** REQUEST CHANGES
**Achados:** 4 Critical, 3 Important, 1 Minor

## Achados

### FE-01 — `output_eu` não tem onde morar no modelo de dados do frontend [Critical]
**Seção:** §4.1-2/3, §6.4-1
**Problema:** a spec diz que `output_eu` é campo novo "no `config` de `script` e de `tfs`". No frontend não existe nenhum objeto `config` aninhado — `DadosScript`/`DadosTfs` (`frontend/src/features/flows/graph.ts`, tipo `DadosScript = DadosBase & { n_inputs: number; n_outputs: number; code: string }` e `DadosTfs = DadosBase & { matrix: MatrizTfs }`) são **planos**: `exec_order`/`label`/campos de config convivem no mesmo nível dentro de `data`. O próprio comentário do arquivo confirma a convenção: "`data` carrega **apenas** as chaves que o servidor aceita (`exec_order`, `label` e a config do tipo)" (`graph.ts:18-19`) — ou seja "a config do tipo" já significa os campos soltos, não um objeto `config` literal.
**Evidência:** `frontend/src/features/flows/graph.ts` (tipos `DadosScript`/`DadosTfs`, e comentário `:18-20`); backend `packages/ottima-core/src/ottima_core/flowgraph/parse.py:19-22` — `_CONFIG_KEYS["script"] = ("n_inputs", "n_outputs", "code")` (plano, sem chave `config`) — e `:252-255`: `allowed = {"exec_order", "label", *_CONFIG_KEYS[node_type]}`; toda chave de `data` fora desse conjunto vira `"chave desconhecida em 'data': '<key>'"` (422).
**Consequência:** um implementador que seguir a letra da spec ("no `config` de script e de tfs") e criar `data.config = { output_eu: {...} }` no frontend faz o backend recusar com 422 assim que a chave literal `"config"` chegar em `data` — ela não está em `_CONFIG_KEYS["script"]`/`_CONFIG_KEYS["tfs"]` nem nunca poderia estar (o backend também é plano). O bloco Script/TFS fica impossível de salvar com EU configurado. Mesmo que o backend seja corrigido para aceitar `output_eu` em `_CONFIG_KEYS` (spec §4.1-3 já prevê isso do lado backend), o frontend precisa emitir `output_eu` como **irmão** de `n_inputs`/`n_outputs`/`code` (script) ou de `matrix` (tfs) dentro de `data`, nunca aninhado.
**Correção sugerida:** trocar `DadosScript = DadosBase & { n_inputs: number; n_outputs: number; code: string; output_eu: Record<string, string> }` e `DadosTfs = DadosBase & { matrix: MatrizTfs; output_eu: Record<string, string> }` (planos, mesma forma dos demais campos), e a mesma forma em `NoSerializado`/`paraGraphJson`/`deGraphJson` (`graph.ts`). Reescrever §4.1-2 para dizer explicitamente "campo novo `output_eu`, irmão de `n_inputs`/`n_outputs`/`code` (script) e de `matrix` (tfs) dentro de `data` — não um objeto `config` aninhado" para não induzir a nesting incorreta.

### FE-02 — Campo de EU por porta de saída do Script exige tornar `n_outputs` controlado, o que quebra o padrão atual do modal [Important]
**Seção:** §6.4-1
**Problema:** `ModalConfigBloco.tsx` é deliberadamente não-controlado: "Os campos são não-controlados e lidos no envio; só `enabled`/`kind` da matriz do TFS vivem em estado, porque decidem quais parâmetros existem" (comentário do arquivo). `CamposScript` renderiza `n_outputs` como um `<Select defaultValue=...>` sem `onChange` — nada observa o valor **atual** selecionado no DOM. Um campo de unidade "por porta de saída" (§6.4-1) para Script precisa saber quantas portas OUT existem **no momento em que o formulário está aberto**, o que exige que a contagem de OUTs vire estado controlado (como já é feito para `enabled`/`kind` do TFS) — mudança estrutural no modal que a spec não menciona.
**Evidência:** `frontend/src/features/flows/config/ModalConfigBloco.tsx:70-113` (`CamposScript`, `<Select id="n_outputs" ... defaultValue={dados.n_outputs}>` sem `onChange`) e comentário de topo do `ModalConfigBloco` sobre campos não-controlados.
**Consequência:** dois implementadores resolvem diferente — um levanta `n_outputs` para estado do modal (replicando o padrão já usado para `matrizTfs`), outro tenta um "hack" de ler o DOM via `ref`/`FormData` a cada tecla. TFS não tem esse problema porque `y1`/`y2` são fixos (não dependem de nenhuma escolha do usuário).
**Correção sugerida:** adicionar `n_outputs` ao estado do `ModalConfigBloco` (mesmo padrão de `matrizTfs`), com `onChange` no `<Select>`, e derivar a lista de campos de EU de `OUT1..OUT{nOutputsAtual}` a partir desse estado — igual ao que já se faz para `enabled`/`kind` da matriz TFS.

### FE-03 — Download autenticado (export de projeto e `.der` do certificado) não tem caminho executável com o `api()` atual [Critical]
**Seção:** §6.1-5, §6.2 (botão "Baixar .der"), §3.1-2
**Problema:** a API usa JWT via header (`Authorization: Bearer <token>`, `frontend/src/lib/api.ts:52`), não cookie — um `<a href="/api/projects/{id}/export">` simples não carrega esse header (navegação de âncora não anexa headers customizados), então o backend (rota `require_admin`) devolveria 401 antes mesmo de gerar o arquivo. Além disso o helper `api()` não serve para nenhum dos dois downloads: ele sempre faz `await res.text()` seguido de `JSON.parse(corpo)` (`api.ts:64-66`) e **nunca expõe os headers da resposta** — não há como ler `Content-Disposition` para o nome do arquivo, e no caso do `.der` (binário real, não JSON) o `JSON.parse` sobre o texto decodificado quebra o conteúdo binário (decodificação UTF-8 com perda) e depois falha ao dar parse.
**Evidência:** `frontend/src/lib/api.ts:47-67` (função `api`, sem acesso a `res.headers` nem a `res.blob()`); `frontend/src/lib/api.ts:25-33` (`getToken`/token só em `localStorage`, nunca cookie). Busca em todo `frontend/src` não encontrou nenhum uso prévio de `Blob`/`createObjectURL`/`res.blob()`/`Content-Disposition` — não existe padrão a copiar.
**Consequência:** como está escrito, a spec deixa a tarefa "salva o arquivo pelo `Content-Disposition`" (§6.1-5) e "Baixar .der" (§6.2) sem primitivo viável — B-F6-03 e B-F6-05 do roteiro L3 dependem exatamente desse fluxo funcionar pela UI.
**Correção sugerida:** especificar um segundo helper em `lib/api.ts` (ex.: `baixarArquivo(path): Promise<{blob: Blob; nomeArquivo: string}>`) que faz `fetch` bruto com o `Authorization` (reusando `getToken()`), lê `res.blob()` e `res.headers.get("Content-Disposition")` (parse do `filename=`), e do lado do chamador cria `URL.createObjectURL` + `<a>` sintético + `revokeObjectURL`. `api()` continua intocado para os demais endpoints JSON.

### FE-04 — `api()` força `Content-Type: application/json` em qualquer corpo; o "mesmo primitivo" de upload do §6.2-3 não serve ao import do §6.1-6 sem modificação [Critical]
**Seção:** §6.2-3, §6.1-6
**Problema:** `api()` sempre executa `if (init?.body) headers.set("Content-Type", "application/json")` (`api.ts:49`) — isso **sobrescreve** qualquer `Content-Type` que o chamador tenha passado em `init.headers` (o `Headers.set` do passo seguinte vence o que veio antes), mesmo quando `body` é um `Blob`/`ArrayBuffer`. O endpoint de trust de certificado do servidor exige corpo bruto `application/octet-stream`/`application/x-pem-file`/`application/pkix-cert` (spec §6.2-3, `connections.py:259-263`) — se o upload passar por `api()` sem alteração, o servidor recebe `Content-Type: application/json` sobre bytes binários. Além disso, §6.1-6 chama a seleção de arquivo do import de "primitivo de §6.2-3" (`File.arrayBuffer()` → `Blob` → corpo bruto), mas o corpo do import é **JSON** (`{"name": "...", "bundle": {…}}`, §3.2-1) — o arquivo precisa ser lido como **texto** e `JSON.parse`ado no cliente para entrar no campo `bundle`, não jogado cru no corpo da requisição. São dois primitivos de leitura de arquivo genuinamente diferentes (bytes brutos vs. texto+parse) sendo descritos como um só.
**Evidência:** `frontend/src/lib/api.ts:47-50` (`api()`, `Content-Type` forçado incondicionalmente sempre que há `body`); busca em `frontend/src` confirma que não existe hoje nenhum `type="file"`/`accept`/upload binário — a spec já reconhece isso em §6.2-3 ("Não existe hoje nenhum `type='file'`... em todo o `frontend/`").
**Consequência:** o upload de certificado, se implementado passando o `Blob` por `api()` sem tocar no helper, falha silenciosamente contra `application/octet-stream` esperado pelo backend. E se o import reusar literalmente `File.arrayBuffer()` → `Blob` → corpo bruto (lendo a spec §6.1-6 ao pé da letra), o corpo do `POST /api/projects/import` sai como bytes crus do arquivo, não como `{"name", "bundle"}` — 422 de forma imediato (camada 2, Pydantic).
**Correção sugerida:** (a) `api()` só deve setar `Content-Type: application/json` quando `init.body` for `string`/ausente; para `Blob`/`ArrayBuffer` deve preservar o `Content-Type` explícito do chamador (ou não setar nenhum, deixando o navegador inferir do `Blob`). (b) Documentar dois primitivos distintos: upload binário (certificado) = `File.arrayBuffer()` → `Blob` → corpo bruto com `Content-Type` do arquivo; leitura de bundle (import) = `File.text()` → `JSON.parse` → embutido em `{name, bundle}` → `api()` normal (que já funciona sem mudança nenhuma para este caso, por já ser JSON). Só o gesto "`<input type=file>` oculto acionado por botão" é de fato compartilhável entre os dois — não a serialização.

### FE-05 — Nenhuma invalidação de `queryKey` especificada para `["projects"]`; reintroduz o próprio bug que a §6.1 existe para fechar [Critical]
**Seção:** §6.1-4 (Ativar), §6.1-6 (Importar), §9.1 (não menciona cache)
**Problema:** `useActiveProject()` — usado por `ConnectionsPage`, `FlowsPage`, `TagsPage` e `OperateSelectorPage` para decidir se mostra "Nenhum projeto ativo" — lê `queryKey: ["projects"]` (`frontend/src/features/connections/useConnections.ts:14-19`), uma string literal solta, sem `CHAVE` exportada e sem nenhuma mutação hoje que a invalide (não existe hoje nenhuma tela que crie/edite/ative/exclua projeto — é exatamente a lacuna que a §6.1 fecha, conforme a própria spec registra em §1, fato 3). A spec especifica as mutações **Ativar** e **Importar** em detalhe (§6.1-4/6), mas não diz uma palavra sobre invalidar cache do React Query em nenhuma delas.
**Evidência:** `frontend/src/features/connections/useConnections.ts:14-19` (`useActiveProject`, `queryKey: ["projects"]`, sem `CHAVE` const, sem `invalidateQueries` em lugar nenhum do arquivo); padrão existente de invalidação em `useCreateConnection`/`useUpdateConnection`/`useDeleteConnection` (mesmo arquivo, `:30-58`) que sempre chamam `queryClient.invalidateQueries({queryKey: CHAVE})` no `onSuccess` — convenção que a nova página de Projetos precisa seguir e a spec não nomeia.
**Consequência:** sem invalidar `["projects"]` no `onSuccess` de Ativar, as quatro telas citadas pela própria spec como "presas" (§1, fato 3) continuam presas **depois** da ativação — o admin ativa o projeto na tela nova, mas `ConnectionsPage`/`FlowsPage`/`TagsPage`/`OperateSelectorPage` seguem mostrando o estado antigo até um reload manual, porque cada uma tem sua própria instância de `useActiveProject()` com cache TanStack Query não invalidado. É o mesmo "esquecimento clássico" que a tarefa pede para verificar — confirmado. Sem invalidar depois de Importar, a tabela da própria página `/engenharia/projetos` não mostra o projeto recém-importado sem reload manual (B-F6-06 do roteiro pede navegação imediata para Conexões com o resumo — plausível de passar mesmo com esse bug, mas o item da tabela "Projetos" continuaria velho).
**Correção sugerida:** exportar uma `CHAVE_PROJETOS = ["projects"] as const` (substituindo a string solta), e toda mutação nova de projeto (criar/editar/excluir/ativar/importar) chamar `queryClient.invalidateQueries({queryKey: CHAVE_PROJETOS})` no `onSuccess`, seguindo o padrão de `useConnections.ts`. Registrar explicitamente em §6.1 e/ou §9.1.

### FE-06 — Tique de TTL "no provider" não diz como chega até `AnnunciatorBar`; a forma óbvia (bump no `EstadoContext`) re-renderiza toda página que usa `useCanalAoVivo` [Important]
**Seção:** §6.6-1
**Problema:** `resolverAlarmes` **já** recebe `agora: Date` como parâmetro (confirmado — não é uma lacuna de assinatura). Hoje ele é chamado em dois lugares independentes, cada um com seu próprio `new Date()`: (1) `AnnunciatorBar.tsx:68`, num `useMemo` cujas deps são `[eventos, flowStatus, mpcStates]` — **sem** dependência de tempo; e (2) dentro do próprio provider, num `useEffect` (`CanalAoVivo.tsx:644-647`) só para sincronizar assinaturas, cujas deps são `[estado.eventos, estado.flowStatus, estado.mpcStates, registro, sincronizadorCondicoes]` — também sem tempo. "Tique de 5s no `CanalAoVivoProvider`" (§6.6-1) não diz como o novo tique chega a esses dois `useMemo`/`useEffect` para forçar reavaliação. O caminho mecanicamente óbvio — o provider fazer `setEstado` (ou expor um novo campo tipo `agora`) a cada 5s via o mesmo `EstadoContext` que já alimenta `useCanalAoVivo()` — força **toda** página que chama `useCanalAoVivo()` (não só `AnnunciatorBar`) a re-renderizar a cada 5s, mesmo sem nenhuma mensagem nova: `EventsPage.tsx:102`, `OperatePage.tsx:94` (tela de operação, com `TrendOperacao` uPlot + `FaceplatePrincipal`/`FaceplateVariavel`) e `FlowEditorPage.tsx` via `useFlowStatus` → `useCanalAoVivo` (`useFlowStatus.ts:178-181`) são todos consumidores diretos do mesmo `EstadoContext.Provider value={estado}` (`CanalAoVivo.tsx:702-704`, um único objeto, sem seletor por campo).
**Evidência:** `frontend/src/app/CanalAoVivo.tsx:233-236` (assinatura de `resolverAlarmes` com `agora`), `:645-647` (chamada dentro do `useEffect` de sincronização, sem tique), `:701-704` (`EstadoContext.Provider value={estado}`, contexto único); `frontend/src/app/AnnunciatorBar.tsx:65-70` (`useMemo` local, sem tique); consumidores de `useCanalAoVivo`: `EventsPage.tsx:4,102`, `OperatePage.tsx:3,94`, `useFlowStatus.ts:3,178-181` (usado por `FlowEditorPage.tsx:193`).
**Consequência:** a condição TTL cessar sozinha (B-F6-11) é alcançável de mais de uma forma, e a forma mais direta de implementar "tique no provider" tem custo de re-render a cada 5s em telas que hoje só re-renderizam quando chega mensagem de verdade — inclusive a tela de Operação, que é justamente onde a tarefa pede atenção a esse custo (trend uPlot + faceplates).
**Correção sugerida:** especificar que o tique deve viver **fora** de `EstadoContext` — por exemplo um terceiro context (`TickContext`, atualizado a cada 5s, consumido só por `AnnunciatorBar`) ou um `setInterval` local dentro do próprio `AnnunciatorBar` (mais simples, já que ele é o único componente hoje que renderiza a partir de `resolverAlarmes`) — e resolver separadamente como o `useEffect` de sincronização de assinaturas (`:644-647`, que também precisa do tique para desassinar `mpc_state`/`flow_status` quando a condição TTL cessa) recebe o mesmo pulso sem depender de `EstadoContext` mudar de referência.

### FE-07 — Confirmado: existe exatamente **um** ciclo de import em runtime (não mais de um); a correção não nomeia o módulo neutro nem quais símbolos migram [Minor]
**Seção:** §6.6-2
**Problema:** confirmado o ciclo real: `CanalAoVivo.tsx` importa (como **valores**) `atrasoReconexao, deveReconectar, ehEstado, lerPorts, mesclarPorts, objeto, urlDoWs` de `useFlowStatus.ts`; e `useFlowStatus.ts` importa (como **valores**) `useAssinatura, useCanalAoVivo` de `CanalAoVivo.tsx`. É seguro hoje porque nenhum dos dois lados usa o símbolo importado no topo do módulo (só dentro de corpos de função), como a spec diz. Há também dois `import type { EventMessage } from "./CanalAoVivo"` (em `alarmes.ts` e `bootstrapAlarmes.ts`) que **não** formam um segundo ciclo em runtime: `import type` é sempre apagado na compilação — o sentido `CanalAoVivo.tsx → alarmes.ts` (valores: `chaveMpc`, `resolverAlarmes`) é de mão única depois de erasure. Confirmado: **só um ciclo real**. A correção da spec ("primitivos compartilhados extraídos para módulo neutro") não nomeia nem o conjunto de símbolos nem o arquivo destino — ambíguo o bastante para dois implementadores escolherem límites diferentes, embora `useFlowStatus.ts` já demarque a seção com o comentário "Protocolo (§5.3) — puro, reusado pelo provider da sessão" (`useFlowStatus.ts`, seção "Protocolo"), o que reduz bastante a ambiguidade real.
**Evidência:** `frontend/src/app/CanalAoVivo.tsx:13-25` (import de valores de `useFlowStatus`); `frontend/src/features/flows/useFlowStatus.ts:3` (import de valores de `CanalAoVivo`); `frontend/src/app/alarmes.ts:3` e `frontend/src/app/bootstrapAlarmes.ts:2` (`import type` — mão única após erasure).
**Consequência:** baixa — o refactor é mecânico e o corte já está sinalizado no código-fonte por comentário, mas a spec, ao não nomear o arquivo destino, deixa dois PRs plausíveis com nomes diferentes (`wsProtocol.ts` vs. algo dentro de `lib/`) sem um "certo" documentado; e não observa que **só é preciso mover o lado que sai de `useFlowStatus.ts`** para `CanalAoVivo.tsx` parar de importar de lá — o outro sentido (`useFlowStatus.ts` → `CanalAoVivo.tsx`, para `useAssinatura`/`useCanalAoVivo`/`EstadoDoCanal`) pode continuar como está, porque deixa de ser cíclico assim que o primeiro lado sai.
**Correção sugerida:** nomear o módulo destino (ex.: `frontend/src/features/flows/wsProtocol.ts`) e a lista exata de símbolos a mover: `urlDoWs`, `atrasoReconexao`, `deveReconectar`, `ehEstado`, `lerPorts`, `mesclarPorts`, `objeto`, mais os tipos `AmbienteAoVivo`/`FlowStatus`/`PortsPorBloco` — a seção já demarcada como "Protocolo" em `useFlowStatus.ts`. `CanalAoVivo.tsx` e `useFlowStatus.ts` passam a importar dali; `useFlowStatus.ts` continua importando `useAssinatura`/`useCanalAoVivo`/`EstadoDoCanal` de `CanalAoVivo.tsx` sem problema (deixa de ser cíclico).

### FE-08 — "Reusa byte a byte os padrões de `ConnectionsPage`/`FlowsPage`" (A-13) superestima o que é reaproveitável — não existe componente de tabela compartilhado [Important]
**Seção:** §6.1-2, Anexo A-13
**Problema:** `ConnectionsPage.tsx` e `FlowsPage.tsx` não importam nenhum componente de tabela/CRUD genérico — cada uma reimplementa a própria marcação `<table>`, o array `COLUNAS`, o loop do `<thead>`, as linhas de carregando/erro/vazio, e o padrão local `aConfirmar`/`erro` (confirmado: nenhuma das duas importa um `Table`/`DataTable`; só `Card`/`Button`/`Input`/`Select` de `components/ui/`). "Reusa byte a byte" sugere que existe algo para *importar*; na realidade existe apenas uma **convenção visual a copiar à mão** — e há três interações na página de Projetos sem qualquer precedente nas duas páginas citadas: (1) confirmação de **Ativar** com o efeito escrito por extenso (§6.1-4 — as duas páginas só têm confirmação inline simples de exclusão, sem texto de efeito, `ConnectionsPage.tsx`/`FlowsPage.tsx` não têm nada parecido com "encerra a execução de todos os flows..."); (2) **Exportar** por linha (download autenticado, ver FE-03 — nenhuma das duas páginas tem ação de download); (3) **Importar** no cabeçalho (upload + resumo de `pending_secrets` + `detail` agregado — nenhuma das duas tem upload nem um painel de resumo pós-mutação).
**Evidência:** `frontend/src/features/connections/ConnectionsPage.tsx:1-9` (imports, sem componente de tabela) e `:157-163` (`<table>` bruta); `frontend/src/features/flows/FlowsPage.tsx:1-11` (imports) e `:274-280` (`<table>` bruta); ausência confirmada de qualquer `DataTable`/tabela compartilhada em `frontend/src/components/ui/` (só `button.tsx`, `card.tsx`, `input.tsx`, `label.tsx`, `select.tsx`).
**Consequência:** não bloqueia a tarefa, mas a frase "byte a byte" no Anexo A-13 subestima o esforço real — o que de fato é reaproveitável é: casca de `Card` + `<table>`, loop de `COLUNAS`/`<thead>`, linhas de carregando/vazio/erro, gate `useCanMutate`/`podeMutar`/`totalColunas`, e o padrão inline de confirmação simples (`aConfirmar === id`) só para **Excluir**. Tudo o mais em §6.1 (Ativar com texto de efeito, Exportar, Importar com resumo) é código novo sem análogo hoje.
**Correção sugerida:** reformular A-13/§6.1-2 para: "reusa a casca de tabela (`Card` + `<table>` + colunas + estados de carregando/vazio/erro + gate `useCanMutate`) de `ConnectionsPage`/`FlowsPage`; Ativar, Exportar e Importar são interações novas, sem análogo nas duas páginas".

## Verificações positivas

1. **`AcaoPendencia.state: MpcState → unknown` (§6.6-3) é seguro e completo como escrito.** `reduzirPendencia` (`frontend/src/features/operate/pendencia.ts:50-54`) só usa `acao.state` através de `lerCaminho(objeto: unknown, caminho: string): unknown` — já trata o valor como `unknown` internamente, sem nenhum acesso tipado a `MpcState`. Os dois pontos de despacho continuam válidos sem cast: `FaceplatePrincipal.tsx:176` (`state: mpcState`, já um `MpcState` completo — atribuível a `unknown` sem cast) e `FaceplateVariavel.tsx:148-150`, onde o double-cast `as unknown as MpcState` **deixa de ser necessário** — pode virar `state: { vars: { [definicao.id]: valor } }` direto. Nenhum outro consumidor de `AcaoPendencia`/`state` encontrado no repo.
2. **`resolverAlarmes` já recebe `agora: Date` como parâmetro** (`app/alarmes.ts:233-236`) — o tique de §6.6-1 realmente não muda a assinatura da função, só precisa mudar quem a chama e com que cadência (ver FE-06 para o "onde" e o custo).
3. **Rota nova em `router.tsx` e item de nav em `AppShell.tsx` (§6.1-1) são mecânicos e sem armadilha** — o padrão de `<Route path="/engenharia/..." element={...}/>` dentro do grupo `AppShell`/`AuthGuard` e o array `NAV_ENGENHARIA` já seguem convenção uniforme; adicionar "Projetos" replica exatamente a forma dos quatro itens existentes.
4. **Handles de saída do Script/TFS citados em §4.1-3 (`OUT1..OUTn`, `y1`/`y2`) já existem no lado do editor** — `portasScript`/`handlesSaida` (`graph.ts`) já geram esses nomes; o campo de UI de §6.4-1 pode reaproveitar essas funções para gerar os rótulos das entradas de EU (uma vez resolvido FE-01/FE-02).
